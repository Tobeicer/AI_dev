# 最低充分实现

目标是在理解需求和真实调用链之后，选择能够完整满足当前目标的最简单实现。最小化的是不必要的拥有成本，不是理解、正确性或用户要求。

## 先理解再收缩

- 读取直接相关的现有实现、调用者、契约和测试，确认实际影响面。
- 不把用户描述的症状直接当作根因，也不为了缩小 diff 在错误层级打补丁。
- 任务明确时直接执行，不把理解过程扩张为新的规划、研究、文档或审批流程。

## 按实现阶梯选择

在第一个能够完整满足当前目标的层级停止：

1. 现有行为或配置。
2. 项目已有的正式实现、共享工具或惯用模式。
3. 语言标准库、框架或平台原生能力，以及数据库等基础设施已有约束。
4. 已安装且适合当前问题的依赖。
5. 为当前需求编写的最少新代码。

把这条阶梯当作选择方法，不要机械地逐项研究。多个方案都正确时，优先选择总体复杂度更低、边界行为可靠且与项目一致的方案。

## 在正确层级只实现一次

- 修复问题时定位根因和相关调用者；适合统一处理时，在公共收口点修复。
- 不暗中创建新版、重写版、平行实现或替代链路。
- 避免没有当前用途的接口、工厂、包装层、常量配置化、未来脚手架和重复辅助函数。
- 只有新依赖能解决当前问题且使总体复杂度更低时才引入它。
- 优先最小正确 diff 和较少文件，但不以牺牲可读性、项目架构或明确需求为代价。
- 可以安全删除真正冗余的代码，但删除不是目标；保留用户已有改动。

## 保持完整并适度验证

- 不以“简单”为由删减明确需求、必要的错误处理、数据保护或真实信任边界上的校验。
- 有意采用存在上限的简单方案时，说明已知上限和可观察的升级触发条件，不提前实现升级方案。
- 对非平凡逻辑执行覆盖真实风险的最小可运行验证；优先复用现有测试，不为简单改动新建测试框架或大批夹具。
- 最小方案与扩展方案都可行时，先完成最小方案；可选扩展放在结果之后说明，不把它变成执行前的确认门槛。

## 交付

- 先报告已经完成的结果。
- 仅在有助于判断时简要说明复用了什么、刻意没有新增什么，以及何时需要升级。
- 未满足明确验收条件时，不把缩减版或局部结果宣称为完成。
