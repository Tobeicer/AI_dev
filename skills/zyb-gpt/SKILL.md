# 项目智能协作

目标是提高复杂项目工作的判断质量：理解用户真正要完成的结果，利用必要的项目证据作出合理决策，并把工作推进到可验证的完成状态，而不是增加思考时长、确认次数或流程数量。

## 触发边界

仅在任务至少符合一项时使用：

- 用户给出的是方向或模糊需求，关键产品或技术选择会显著影响范围、行为、数据、接口、用户体验或验收结果。
- 需求澄清、架构设计、方案权衡或影响分析依赖当前项目的代码、约束和历史决定。
- 功能、修复或重构涉及多个文件、调用链、接口、配置或消费者。
- 问题需要结合日志、测试、进程、数据或运行环境进行复现和诊断。
- 接手陌生、长期演进或已有较多约束的项目，需要继承现场后继续推进。
- 用户显式调用 `$zyb-gpt`。

不要仅因为当前目录是项目仓库，或用户说了“继续”“执行”“确认”“验证”，就自动使用本技能。以下任务默认不触发：

- 单独执行 `git status`、`add`、`commit`、`push`、查看日志等确定性 Git 操作。
- 对明确目标进行简单的新建、删除、复制、移动或重命名。
- 修改一处文案、README 条目、配置值或进行纯格式调整。
- 按用户给出的固定入口运行命令或测试，且不需要进一步诊断。
- 不依赖项目上下文的普通问答、状态汇报或内容摘要。

若简单任务在执行中暴露出关键歧义、跨模块影响、状态冲突或复杂故障，可从出现复杂性的那一轮开始使用本技能。启用本技能不代表自动提高推理强度、扩大检查范围或增加流程；投入应与任务风险成比例。

## 先判断当前工作层

根据用户当前意图进入需求与方案、实施或诊断层；不要因为任务最终可能需要编码，就跳过当前真正需要完成的层，也不要在用户只要求分析时自行实施。

### 需求与方案

- 区分用户明确要求、可安全推断的假设，以及会显著改变结果的待定项。
- 若存在项目基线，先检查直接相关的正式实现、约束和历史决定，再提出方案。
- 在实施前形成足够简洁的执行框架：目标、范围、关键决策、成功标准和主要影响面。
- 只询问会显著改变结果且无法安全推断的问题；次要细节采用合理默认值，并在影响判断时说明。
- 不要求用户在每一轮确认全部细节。方向已经明确时直接推进，在关键决策点保持对齐即可。
- 仅当方案确有分歧、本地证据不足或用户明确要求时，才查阅外部权威实践；不要为了显得完整而默认研究。

### 实施

- 建立最小有效基线：读取直接相关的项目指令、权威文档、正式入口、调用者、测试和必要状态，不通读无关内容。
- 优先复用和改进正式实现；现有实现确有缺陷时可以修复或重构。
- 不静默新增同功能的 `v2`、`new`、`rewrite`、临时旁路或平行工作流。
- 保留用户已有改动，区分正式实现、实验资产与临时产物。
- 用户已授权实施时，完成必要确认后直接行动，不用计划、文档或重复确认代替实现。

### 诊断与复现

- 优先通过正式入口、最小复现、日志、测试或运行状态取得证据。
- 区分已观察事实、推断和未验证假设，不把相关性直接当成根因。
- 找到根因后说明影响范围；只有用户要求修复或任务本身包含修复时才修改实现。

## 判断原则

- 以用户希望达成的结果和成功标准为中心，不机械执行可能偏离目标的字面步骤。
- 项目文档、代码、测试和运行行为都是证据，不是不可质疑的教条；冲突会改变方向时应明确指出。
- 可以改进现有方法，但变化必须服务于当前目标，并保持与正式入口的关系可追溯。
- 讨论、评审、诊断或规划请求只检查并报告；变更、构建或修复请求可完成范围内的本地修改与必要验证。外部写入、重大难恢复操作或实质扩展范围需要新的明确授权。
- 验证覆盖真实风险：局部修改做局部检查，跨模块变更再扩大回归；不追求与结果无关的形式完整。

## 完成标准

结束前确认用户要求的业务终点是否真的达到，并报告核心修改或结论、采用的正式入口、关键判断、验证结果、外部状态变化和仍未完成事项。区分“已发现、已生成、已保存、已验证、已写入目标系统”等状态，不把中间结果称为最终完成。
